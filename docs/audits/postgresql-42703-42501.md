# PostgreSQL 42703 and 42501 audit

Date: 2026-10-30

## Confirmed diagnosis

The Render API runtime role has active pooled connections to the `rass_sprint1_tests`
database on the `development-sprint-1` Neon branch. Earlier schema checks targeted
`neondb`, which is a different database on the same branch.

`rass_sprint1_tests` has migrations through `FinancialNotifications`, but does not
have `AccountOverdraftLimit` or `AccountClassification`.

Consequences:

- `42703`: the current API maps `Accounts.OverdraftLimit`, `IncludeInNetWorth`,
  `Institution`, `Subtype`, and `Type`, which are absent from that database.
- `42501`: the runtime role has no `SELECT`, `INSERT`, or `UPDATE` grant for
  `ExpenseReductionGoals` and `FinancialNotifications` in that database.
- `InvalidOperationException`: a separate application guard can occur when a
  tenant transaction cannot be established. The previous log did not include the
  endpoint, so it could not be correlated safely.

RLS remains enabled and forced for the audited financial tables. The runtime role
has no superuser, `BYPASSRLS`, create-role, or create-database privilege.

## Local corrections

- `DatabaseSafety` now requires `AccountClassification`, preventing an older schema
  from appearing ready and failing later during a finance query.
- The runtime bootstrap script grants the two financial tables introduced by prior
  migrations. This matters whenever grants are reapplied after migrations.
- The exception handler logs route, sync operation classification, SQLSTATE, and
  PostgreSQL table/column/constraint metadata when supplied. It does not log SQL,
  parameters, tokens, credentials, or financial payloads.

## Remote correction required

Apply these existing, versioned EF migrations to **`development-sprint-1` /
`rass_sprint1_tests`**, not to the Neon `production` branch:

1. `20261019020450_AccountOverdraftLimit`
2. `20261030104319_AccountClassification`

They add the five account columns and preserve existing data through defaults.
The latest migration also applies no broad privilege grant; the established runtime
bootstrap must be applied by the migration owner when grants need to be reconciled.

## Validation after approval

1. Confirm both migration IDs in `app."__EFMigrationsHistory"` in `rass_sprint1_tests`.
2. Confirm the five account columns and the grants for `ExpenseReductionGoals` and
   `FinancialNotifications`.
3. Call `/health/ready`; it must be healthy only after the expected migration exists.
4. Sign in, load accounts/categories/transactions, and run a sync pull/push.
5. Validate user and tenant isolation with distinct authorized contexts.

## Rollback

Do not run migration `Down` operations against user data as a routine rollback.
If migration validation fails, stop the API deployment, keep the database unchanged
beyond the applied migration, and restore only from a verified Neon branch or
backup under an approved recovery procedure.
